# 简单使用，后台自动分流

日常只需维护「重要提醒收件人」和 TG 频道；普通提醒发 TG，重要告警加发邮件，TG 明确未受理时邮件兜底。三个开关放在默认收起的「高级规则」中。邮件服务和旧联系人资料收在「邮件服务与其他联系人」中，不影响已保存的数据。

网页发送和通道测试由现有管理员／风控总监登录权限保护，无需每次复制发送授权码。旧服务端 Bearer 授权方式保留兼容。

## 后台规则

- 普通预警与状态通知：TG。
- 击穿、尚有补仓缺口、严重闪跌：按高级规则启用 TG + 核心负责人邮件；不会向全体客户或商务经理群发。
- TG 明确未受理：启用兜底时发送邮件；普通事件转入邮件后不重复向 TG 补发。
- TG 超时、异常响应、长消息部分发布：未知结果暂停该渠道，需人工核查；重要告警原本要求的邮件仍会发送。
- 同批次、同类、同级风险30分钟内去重，冷却从最后处理结果计算，避免积压恢复后立即重复发送。风险升级及新补仓轮次不被较低级别／旧轮次吞掉。
- 未完成或待核查的同类事件继续合并，不因跨过30分钟或停机超过一小时建立重复投递。
- 已受理的渠道和邮箱不重发；明确失败按1、2、4分钟等退避，最长30分钟重试。尚未发送的邮箱由后续任务继续处理。
- 超时、进程中断、服务商已受理但数据库回写失败：保留未知状态，不盲目自动重发，避免额外邮件费用。
- 关闭渠道或移除邮箱：后续尝试前重新检查，停止尚未发出的投递；已在途的请求无法撤回。新增渠道或邮箱不会被追加入旧事件。
- 保留最多10个核心邮箱；TG 未读不会触发邮件。未启用 TG 付费广播，不提供每日汇总自动发送。
- 「已人工核查，停止本条重试」只停止该条通知，不表示送达、已读或风险解除；后续新风险事件仍按规则处理。

## 发送记录

「风险警报中心 → 发送记录」是策略通知最新状态的入口：已受理、等待重试、需核查、未启用、已人工核查。浏览器历史记录与通道测试单独展示，不与服务端队列混为一谈。受理不等于送达或已读，实际邮件费用仍以服务商账单为准。

## 部署

1. 配置现有 PostgreSQL 连接，执行 `npm run db:migrate`，包含新增的 `20261112_notification_policy` 迁移，再部署新版本。
2. 保留已测试成功的邮件服务配置；配置 `TELEGRAM_BOT_TOKEN` 及频道，并验证机器人发帖权限。
3. 保存重要提醒收件人，分别做一次通道测试。
4. 持续运行现有 `/api/internal/monitor` 定时任务。它同时处理持久化通知队列；关闭浏览器不会停止后端队列，但没有调度任务就不会自动重试。

迁移为新增通知队列表，不删除历史邮件、WhatsApp、联系人或账本数据。通知策略与频道配置的通用写入路径已封闭，只能使用专用受保护接口。

## 验证与限制

Prisma schema 校验、优化构建、分流／去重／升级／兜底／逐邮箱重试／关闭策略／并发领取／回写失败模拟回归，以及浏览器交互检查。没有可用的真实 PostgreSQL 测试实例，未执行真实数据库集成或生产迁移，也未发送真实邮件／TG 消息。截图使用模拟配置和投递记录。

## 主动发送与自动提醒

- 批次卡片提供「邮件」「TG」两个按钮。主动发送只处理所选通道，不触发另一通道或邮件兜底。
- 主动邮件使用通知设置中的核心负责人邮箱；没有收件邮箱时在发送前明确提示。主动发送不受自动升级／兜底开关影响。
- 正文标注「手动发送」及当前登录人的姓名；身份由服务端读取，不能由浏览器指定。系统触发的风控通知标注「系统自动提醒」。
- 主动发送与自动事件，以及邮件与 TG，使用不同的去重标识；自动事件仍保留原有去重记录。单个通道真正受理后提示发送成功，失败或结果未知保留真实状态，不伪报成功。
- 手动按钮连续点击仍有并发保护和冷却去重；已有未知结果的手动事件不会盲目重发。
