# 运行、备份与核对

本文件提供可运行的操作工具，不等同于实际部署和真实资金验收。系统当前是人工凭证记账，不执行交易或划款。正式接入前由业务负责人核验协议、客户归属、出资、补仓成交和历史结算，并留存签字结果。

## 升级和回退

先保存加密数据库备份与旧版本镜像，再审核并执行 `20261027_authoritative_ledger_auth`、`20261027_valuation_monitoring` 两份增量 SQL。已经应用的脚本不要重复执行。后者只新增四张表，已在本地已有账本数据库执行验证；没有删除原有表或改写旧账本。迁移历史缺完整初始基线，不要直接对生产执行 `db:push` 或未经核对的 `migrate deploy`。

维护窗口暂停资金操作，应用迁移，启动新版本，验证账号权限、健康接口、实际历史和原始凭证对账。回退时先停新版本和监控进程，保留事故时完整备份；由数据库负责人决定恢复目标和新写入数据处理，不能直接用旧备份覆盖已发生业务。新增表可以保留，禁止为了回退删除审计记录。

旧账本若存在未分配客户的补仓，系统拒绝给出商务经理估值或退出结算，需要人工依据凭证制定有审计的修正方案；不会自动按本金摊派。已经发生的错误历史结算也不会被新代码悄悄重算。

## 独立后台监控

浏览器关闭时仍需运行监控。选择其中一种部署方式，并在部署平台配置自动重启和失败告警：

- 常驻 Node 主机：以单独进程运行 `npm run risk:worker`，与 Web 服务共用同一数据库；使用进程管理器，确保退出重启、日志留存和机器重启后拉起。`npm run risk:worker -- --once` 可执行一次。
- 定时平台：每分钟请求 `GET /api/internal/risk-monitor`，带 `Authorization: Bearer <CRON_SECRET>`。密钥单独生成，至少32字符，不写在公开 URL。平台必须支持该路由最长120秒；任务返回503应触发运维告警。

两种方式均需 `MONITOR_ENABLED=true`、`MONITOR_NOTIFICATION_EMAILS`（1至20个有效邮箱），配置真实邮件服务及 `NOTIFICATION_SEND_TOKEN`。先验证获准收件人的真实送达，再启用 `MONITOR_NOTIFICATIONS_ENABLED=true`。默认均禁用。测试脚本注入模拟通道，不发送真实邮件。

数据库租约阻止重复执行；租约10分钟，每个批次及发送任务之前续约。长刷新超时导致租约失效时，任务停止发送。每个风险阶段及待补仓轮次持久化去重；恢复时取消未发送旧预警。只发送邮件预警，不自动调拨资金；报价异常标识为待核对。

发送超时、部分失败或进程意外中断可能是“已受理但结果未知”，因此不盲目重发。处于 SENDING 超过10分钟的记录转 UNKNOWN。管理员/风控可查看 `/api/monitor/notifications`；管理员核对服务商日志后，以登录会话 POST JSON：

```json
{"id":"通知编号","resolution":"CONFIRMED_SENT","evidence":"服务商工单或回执编号及人工核验记录，至少10字"}
```

确认未发送可选择 `CONFIRMED_NOT_SENT` 重新入队。重新发送前，须确认所有收件人均未受理；部分送达要先由运维制定逐收件人处理方案，避免重复通知。确认操作与审计在同一数据库事务内。不要只凭没有收到邮件判断未发送。

管理员/风控登录后读取 `GET /api/health`。任务未启用、邮件配置缺失、十分钟没有成功任务、队列积压、结果未知或数据库异常均不能返回监控就绪。它不代表整个产品已完成生产验收。监控机器自身停机须由部署平台的外部探针告警。

## 实际估值历史

每次成功记账、结算或行情更新，在同一数据库事务记录实际估值。每个批次每个 UTC 小时保存最后一次观测，不补造历史，不是分钟行情或完整审计流水。图表包含认购、补仓、退出现金流变化，不是收益率曲线。旧批次尚无记录时，会标注部分时点未覆盖全部批次；历史合计只代表已记录的批次。商务经理只看到其所属客户的独立持仓历史；结算收益冻结，保留历史。单次读取超过20000条会明确报错，需要归档或扩容，不能静默截断。

## 加密备份与恢复演练

主机需安装与服务端兼容的 `pg_dump`、`pg_restore`、`psql` 并加入 PATH。环境里的 `DATABASE_URL` 是连接源，独立随机 `BACKUP_KEY` 至少32字符。密钥另存密钥管理服务，不随备份一起上传，不提交 Git。

```sh
npm run db:backup -- /secure/offsite/ledger-20261027.rcbackup
```

备份使用 pg_dump 一致性快照、AES-256-GCM 加密和0600文件权限，禁止覆盖已有文件。需要另行配置定时、异地存储、保留策略、磁盘容量监测和每日成功检查。本命令不自动创建远程存储或调度。

准备一个独立空数据库，将 `RESTORE_DATABASE_URL` 指向该库，`RESTORE_CONFIRM_DATABASE` 填该库精确名称，然后：

```sh
npm run db:backup -- restore /secure/offsite/ledger-20261027.rcbackup
```

完整校验密文后才接触目标；拒绝与源库同一地址、端口和名称的数据库，也拒绝非空库和错误确认。恢复在单个数据库事务内执行。不同域名可能是同一数据库的别名，仍需人工核对目标身份，恢复账号应限权于专用空库。应在恢复库逐表比较记录数量及摘要，核对客户持仓和审计记录，并实际启动服务验收；本地演练不能代替生产备份演练。

## 只读凭证对账

准备经独立审核的 JSON，字段示例如下（示例金额不是实际客户数据）：

```json
{
  "sourceDocumentId":"银行/券商凭证包编号",
  "approvedBy":"审核人",
  "asOf":"2026-10-27T00:00:00Z",
  "batches":[{
    "id":"批次实际ID","remainingCapital":100000,"remainingShares":1000,
    "rescueShares":0,"rescueCash":0,"settlementsCount":0,
    "clients":[{"id":"客户实际ID","investmentAmount":70000,"entryStockPrice":100,"bdUserId":"商务经理实际ID","status":"ACTIVE"}],
    "trades":[]
  }]
}
```

每个客户都须列出，已结算客户另填 `clientReceives` 和 `institutionReceives`（实际净支付）。每笔补仓凭证列出 `id, clientId, amount, collateralType, shares, remainingFraction, entryPrice`，现金 entryPrice 为 null。工具比较当前账本，不按 asOf 重建历史；请在暂停记账的维护窗口取得同期凭证。

```sh
npm run db:reconcile -- /secure/approved-reference.json /secure/new-reconciliation-report.json
```

比较内部本金和份额守恒、独立参考余额、客户本金/入场价/归属/状态/结算、补仓明细及已结算笔数；缺失、多余或不一致时非零退出。金额容差0.03、份额1e-8。报告不覆盖已有文件。该工具不写账本，凭证真实性和法律协议仍由业务审核。

## 测试

`npm test` 包含客户持仓归属和部分退出回归。`npm run verify:operations` 只接受空的本地 `riskcontrol_ops_check` 数据库（audit用户、55437端口）。先建表再执行，脚本创建合成业务和临时恢复库，测试后保留测试源库用于检查；重复执行前需明确清理该隔离库。覆盖实际历史权限和事务回滚、重叠监控、去重、未知结果审计处置、过时预警撤销、加密恢复一致性和只读对账正反例。没有真实客户数据、真实资金或外部邮件发送。
